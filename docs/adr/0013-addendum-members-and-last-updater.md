# ADR-013 addendum: member names, last updater and household contract file

**Status:** Accepted (owner decisions of 2026-11-16) · **Extends:** [ADR-013](0013-concurrency-sync.md) · **Cards:** A15 follow-ups, A16

## Addendum (2026-11-16): member names, last-updater column and household contract file
**Evidence:** `pnpm check` passed (717 unit tests), `pnpm test:int` in `apps/server` passed (177 tests) and in `database` (103 tests, includes the 0003 migration test and the cross-household FK rejection), `db:drift` reported "Everything's fine", `pnpm e2e` passed 21 of 22 (the one failure is the unrelated `smoke.spec.ts`, failing before this work). The security review of the diff found no blocking item.
**Finding:** The UI showed "another household member" because member ids (`pickedByMemberId`, `createdByMemberId`) have no readable name, and a `409` on an item edit carries only `currentRevision`, with no indication of who changed the item.
**Decision / change:**
1. **Members endpoint.** Read-only `GET /api/v1/household/members` returns `{items: [{id, displayName}]}` for the session's household only. No email, role, user id or OIDC subject. The household comes from the session and the query is household-scoped. The web caches it for 5 minutes and never blocks rendering on it.
2. **Last updater.** An additive migration (0003) adds nullable `shopping_items.updated_by_member_id` with a composite FK `(household_id, updated_by_member_id)` to `household_members`, like `picked_by_member_id`. The server sets it from the session actor on add, detail edit and checkoff (never from the client; no-ops and idempotent replays leave it unchanged). It is exposed as `ShoppingItem.updatedByMemberId` (nullable). Existing rows stay null and show the generic label. It does not change the `revision` or `change_seq` rules. The column records the last updater of any kind, not only editors: a checkoff sets it without bumping `revision`.
3. **Conflict banner.** On a `409` the item sheet shows the generic label at once, then refetches the list snapshot. It names the member only if that refetch succeeded and the refetched item's `revision` is greater than the revision the user's edit was based on. Otherwise (fetch failed, or only a checkoff happened since) it keeps the generic label, so it never names the wrong person. It never says "You".
4. **Contract layout.** Household endpoints get the OpenAPI tag `household`, and their schemas are defined in `packages/contracts/src/household.ts` (`HouseholdMember`, `HouseholdMemberList`), because later household endpoints (preferences, profile) will land there. `routes.ts` stays the source of truth for the route list.
**Consequences:** One more A-scope endpoint beside those recorded in ADR-013. `ShoppingItem` grows one nullable field, so fixtures and the E2E fake API set it. A16 reruns the flows against the real server; the fake API bumps `revision` on checkoff while the real server does not, which A16 should catch.
**Still to verify:** the banner rule in decision 3 (refetch failure and checkoff-only cases) is covered by web tests added after the review; confirm they pass in the final run. No index on the new FK column, matching `picked_by_member_id` (negligible at household scale).
**Change request:** the frozen database design (shopping items table) and the tech §10 endpoint list mention neither the new column nor the members endpoint. The owner decides whether to amend them at the next baseline revision.
